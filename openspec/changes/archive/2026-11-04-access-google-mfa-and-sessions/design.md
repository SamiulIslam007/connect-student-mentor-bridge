# Design

## Context

See `proposal.md` — Why. Only the state that shapes the approach is recorded here.

**Repository snapshot (verified 2026-11-04, re-check at apply):**

- `services/api/src/identity/better-auth.ts` configures better-auth 1.7.15 with `bearer()` as the only plugin, a Drizzle adapter over the committed schema (`usePlural: true`, `transaction: true`), and a `session.create.before` hook that refuses a non-`ACTIVE` account.
- `BetterAuthIdentityService` is the only file importing library runtime functions; `packages/domain/src/identity.ts` holds the seam and the error codes.
- `apps/web` holds the session token in an httpOnly cookie and calls the API with `Authorization: Bearer`; the API never sets a browser cookie (owner decision, `docs/auth-and-access-control.md` §5).
- `audit_logs.action` is a free-text column with a TypeScript union in `services/api/src/identity/audit-log.ts`.
- `sessions` is the library-native table (`id`, `token`, `user_id`, `expires_at`, `ip_address`, `user_agent`, `created_at`, `updated_at`), reachable through Drizzle.
- Migrations: `services/api/drizzle/NNNN_*.sql`, generated by `pnpm --filter api db:generate`; app-role grants are added by an explicit SQL step (the Sprint 1 audit finding).
- No role table, no `two_factors` table, no `users.two_factor_enabled` column.

## Goals / Non-Goals

**Goals**

- Google sign-in that is inert without credentials and complete with them.
- A TOTP second factor that never leaves secret material in a log, an audit row, or a later response.
- Session list and idempotent per-session revoke.
- Additive schema and one migration; no rewrite of existing rows.

**Non-Goals**

- Role authorization, the permission-matrix test, profile visibility, and admin idle/absolute timeouts — the Sprint 2 change `roles-and-profile-visibility` (4c).
- Email/SMS one-time-code second factors (`otpOptions.sendOTP`), trusted-device cookies, and the security-settings UI beyond the endpoints.
- Rate limiting outside the second-factor paths (Sprint 7).
- Account linking removal, provider de-linking, and provider refresh-token storage.

## Decisions

### D1 — Use the installed `twoFactor` plugin; do not hand-roll TOTP

The plugin ships the secret encryption, TOTP generation, backup-code hashing, the sign-in gate, the attempt counter, and the account lockout. Hand-rolling would duplicate cryptography and add an untested path to the trust core. It is part of `better-auth` 1.7.15, so no dependency is added.

Rejected: a project-owned TOTP implementation (`otplib` and friends) — new dependency, new secret storage, and the same amount of wiring.

### D2 — The MFA challenge is the library's own signed cookie value, relayed as an opaque string

The API does not hold browser cookies, so the challenge cannot live in a cookie between the two API calls. `signInEmail` is called with `returnHeaders: true`; when the body says `twoFactorRedirect`, the service returns the value of the `set-cookie` entry named `<prefix>.two_factor` as `mfa_challenge`. `POST /v1/auth/mfa/verify` reconstructs `Cookie: <prefix>.two_factor=<challenge>` and calls `verifyTOTP`, which consumes the verification row and returns `{ token, user }`.

Consequences: the challenge is opaque, single-use, tamper-evident (the library verifies its HMAC and the `verifications` row), and expires in 10 minutes. The client never sees a token; the BFF stores `mfa_challenge` in its own short-lived cookie.

Rejected: a project-owned challenge token — it would require duplicating the plugin's cookie and verification row or forking the plugin.

### D3 — Provider credentials gate registration, and the endpoints exist either way

`createIdentityAuth` receives `googleClientId` and `googleClientSecret`; `socialProviders.google` is set only when both are non-empty strings. The controller still exposes both provider endpoints: a start request without configuration answers `503 PROVIDER_UNAVAILABLE` (a new problem code), and the service refuses before any library call, so no placeholder identifier can leak into an authorization URL.

Rejected: a boot failure when the credentials are absent — it would break every local stack and CI run; rejected: a default client id — it would be a committed secret-shaped value.

### D4 — The provider callback relays the library's state cookie the same way as the challenge

`signInSocial` returns `{ url }` and sets a signed `state` cookie. The service returns `{ authorizationUrl, state }`, where `state` is that cookie's value. The callback posts `{ provider, code, state }`; the API rebuilds the cookie header and calls the library's OAuth callback, then reads the session token from the returned `set-cookie`. A missing or altered state fails inside the library and surfaces as `401 UNAUTHENTICATED`.

Consequence: the account-linking rule stays the library's default (link by verified email when no other account holds that provider), which is what `docs/auth-and-access-control.md` §4.1 requires.

### D5 — Sessions are read and revoked through the project's own table

`GET /v1/me/sessions` selects from `sessions` by `user_id` with `expires_at > now()` and returns `id`, `created_at`, `updated_at`, `expires_at`, `ip_address`, `user_agent`, and `current` — never `token`. `DELETE /v1/me/sessions/{id}` deletes `WHERE id = $1 AND user_id = $2`; a zero-row result is a success unless the id exists for a *different* user, which is `404`. The library is not involved: its `revokeSessions` call is all-or-nothing and a per-session path would need a cookie anyway.

Idempotency rule, spelled out: an id that never existed and an id belonging to the caller that is already gone both answer `204`; an id belonging to another account answers `404`. Distinguishing "never existed" from "already revoked" is impossible by design (rows are deleted), and both are the caller's own outcome, so no information is lost.

### D6 — Audit actions are added to the union, not to a table enum

`AuditAction` gains `MFA_ENROLLED`, `MFA_VERIFIED`, `MFA_VERIFICATION_FAILED`, `MFA_DISABLED`, `SESSION_REVOKED`, and `PROVIDER_SIGN_IN`. Metadata carries the session id or the factor name only — never a code, a secret, a URI, or a backup code.

### D7 — Scope split: 4a ships the three security pieces, 4c ships the role model

`FR-AUTH-07` (role and object authorization), profile visibility, and the admin session timeouts move to `roles-and-profile-visibility` (4c) before `#5`. Rationale: enforcement needs `role_assignments` *and* an endpoint whose policy it guards; shipping the table alone would be untested policy, and shipping a guard with no consumer is dead code. Recorded in `docs/decision-log.md`, `docs/mvp-build-plan.md`, `docs/milestones-and-phases.md`, and `docs/known-debt.md`.

## Risks / Trade-offs

| Risk | Mitigation |
|---|---|
| The relayed challenge depends on a library-internal cookie name | The name is read from the response headers by suffix match (`two_factor`), not hardcoded to a prefix, and a test asserts a sign-in challenge is refused after one successful use. |
| A provider callback that fails mid-flight could leave a half-linked account | Linking is the library's own transaction; the callback path adds no writes of its own, and a refused callback leaves no session. |
| Session revoke bypasses the library's cookie clearing | The BFF clears its cookie when the revoked id is its own current session; the API's guarantee is that the row is gone, so the next request is `401` regardless. |
| Manifest of `two_factors` columns could drift from the plugin | The schema is written from the installed build's `schema.d.mts` (dated above) and an integration test enrolls and verifies against the real database. |
