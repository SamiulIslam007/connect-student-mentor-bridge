# connect — Hermes project context

Hermes loads this file **instead of** `AGENTS.md` (only one project context file is ever loaded, and `.hermes.md` wins). `AGENTS.md` (tracked) and `AGENTS.local.md` (untracked, Samiul's own workflow) stay authoritative for anything not restated here. Nothing below overrides `AGENTS.md` rules 3, 4, 7, 8, 9, 10 or any owner decision.

## 1. What this repo is

connect: a mentorship platform where a student's reported outcome only becomes real when the mentor confirms it, and only counted outcomes build field-scoped reputation. The product value is trust and an auditable, append-only ledger, so correctness and safety outrank speed.

Owner: Samiul (CTO, sole engineer). Replies, code, docs, commit messages and identifiers stay in **English**. Platform: Windows, shell is Git Bash. Monorepo: pnpm workspace — `apps/web` (Next.js 16 App Router), `services/api` (NestJS modular monolith + worker), `packages/{domain,contracts,config}` (domain stays pure TypeScript), `infra/docker`, `compose.yaml` + `compose.dev.yaml`, Postgres + Drizzle, better-auth behind `IdentityService`.

## 2. Truth order

Must never be guessed: `OUT-Q1` (does platform review count an unconfirmed outcome), `FBK-Q1` (feedback visibility), erasure versus the append-only ledger (`docs/data-model.md`).

## 3. Non-negotiables

- Never weaken a trust rule: unconfirmed outcomes never count, the neutrality firewall, append-only ledger, object-level authorization, audit log, consent records, erasure design.
- Never invent facts, numbers, prices, legal claims, versions, paths, flags or test results. Keep the README truth labels (`Plan target`, `Proposed default`, `Illustrative`, `Open decision`, `Deferred (owner decision)`, `Verified`).
- Never read into context, print, or commit `.env`, `opencode.json`, `AGENTS.local.md`, `dbhub.toml`, tokens or keys. `.env.example` carries variable names only.
- Every user-facing string goes through the string catalog (`apps/web/lib/strings.ts`); timestamps in UTC; no floating-point sloppiness for money or scores.
- Keep the ESLint boundaries intact: `packages/domain` stays pure, `apps/web` never imports `services/api`, `services/api` never imports `apps/web`. Never loosen `eslint.config.mjs` to make a change pass.
- Smallest diff that fully works. No speculative abstraction, no new dependency outside the approved change (exact version pin, committed `pnpm-lock.yaml`, `pnpm audit --audit-level high`), no formatter, no import-order tooling.
- No payments, no AI features, no Redis, no WebSocket in the MVP.
- `packages/contracts/openapi.yaml` is the API contract of record; `/healthz` and `/readyz` stay unversioned and unauthenticated.

## 4. Spec-driven flow (OpenSpec CLI)

`openspec` 1.14.3 is installed; drive it directly rather than through the `/opsx` slash commands, which belong to OpenCode.

```
openspec list --json
openspec status --change <name> --json
openspec instructions apply --change <name> --json      # read every contextFiles entry first
openspec instructions <artifact> --change <name> --json
openspec validate --change <name>
openspec archive <name>                                 # only when Samiul asks
```

- One change = one branch = one small task. Order is fixed by `docs/mvp-build-plan.md` §5.
- Steps: explore (optional, only when asked) → propose → **stop for Samiul's review** → apply → review gate → **stop** → archive when Samiul says so → merge.
- Change names are kebab-case with no dates. Branch: `feat/<change-name>`, or `fix/`, `chore/`, `docs/` — never with dates.
- Never edit `openspec/specs/` directly; specs change only through a change's delta specs and `openspec archive`. Never edit `openspec/changes/archive/`.
- Artifacts are English, `SHALL`/`MUST` preserved, every requirement with a testable `#### Scenario:`.
- No second plan: if a skill writes its own plan or notes file, fold the content into the OpenSpec artifact and leave nothing competing behind. Do not adopt planning/orchestration/memory tooling that duplicates OpenSpec and `docs/`.
- An under-specified formula, weight, threshold or policy is a `MATH-FLAG`: cite what the docs say and ask — never invent it.
- Pure tooling work (agent config, scripts, CI) is not an OpenSpec change: its own branch with a `chore(tooling): …` commit.

## 6. Checks (repo root, identical to CI)

```
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

- Local stack is Compose only: `docker compose up` (detached is fine), hot reload via `compose.dev.yaml`. Postgres is published on host port **55432**; containers reach it at `postgres:5432`.
- Integration tests use the dedicated `connect_test` database. Create it if missing: `docker compose exec postgres psql -U connect -d connect -c "CREATE DATABASE connect_test"`. A test that skips because the database is unreachable is **UNVERIFIED**, never a pass. In CI (`CI=true`) a skip fails instead.
- Tests: `node:test` + `node:assert/strict`, sibling `test/<subject>.test.ts`, non-recursive `test/*.test.ts` glob, seams passed as options (no mocking library). API tests run serially.
- Migrations: Drizzle schema in `services/api/src/db/schema/`, `pnpm --filter api db:generate`, forward-only, applied by the owner or an approved script — never through the DB MCP.
- Report only output I actually read; anything else is `UNVERIFIED`. Two-strike rule: if the same fix fails twice, stop and report what was tried, what was observed, and the best hypothesis.

## 7. Git and GitHub lifecycle (agent-run)

Branch from an up-to-date `main`; one branch per change/task; commit after each verified task group; push the feature branch; open the PR; merge only on green; prove the merge.

```
git checkout main && git pull origin main
git checkout -b chore/<task>
git add <explicit paths>            # never `git add -A`, `git add .`, or `-a`
git commit -m "chore(tooling): …"
git push -u origin chore/<task>
gh pr create --base main --head chore/<task> --title "…" --body "…"
gh pr checks <n>                    # checks, images, security must all pass
gh pr merge <n> --merge --delete-branch
git checkout main && git pull origin main && git log --oneline -3
```

- Conventional Commits, lowercase, imperative, summary ≤ 72 chars; body when the reason is not obvious.
- Merge commit only — squash and rebase are disabled on the repo. Forbidden: pushing to `main`, force flags, rebase, amend, tags, `--admin`, ruleset bypass, raw `git merge`, changing remotes or settings.
- A merge is never claimed without the raw `git log --oneline` from `main` in the same report. If any lifecycle step fails, stop and report the exact command and error — no workarounds.
- Before every commit check `git status` and `git diff --staged`; nothing untracked or unrelated from other work may ride along.
- Tooling assets (`AGENTS.md`, `.claude/`, `.opencode/`, `.hermes.md`) are tracked, reviewed like code, and committed on their own `chore(tooling)` branch.

### Why MCP config is not tracked here

Hermes reads MCP servers only from `$HERMES_HOME/config.yaml`; there is no project-level MCP file to commit. So the generic server (`context7`) is global, and the repo-specific one is registered as `connect-db`, pointing at this repo's untracked `dbhub.toml`. Recreate on a fresh machine:

```
hermes config set mcp_servers.context7.url "https://mcp.context7.com/mcp"
hermes config set mcp_servers.context7.connect_timeout 45
hermes config set mcp_servers.connect-db.command npx
hermes config set mcp_servers.connect-db.args '["-y","@bytebase/dbhub@1.4.0","--transport","stdio","--config","<repo>/dbhub.toml"]'
hermes config set mcp_servers.connect-db.connect_timeout 120
```
